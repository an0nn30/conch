# Pop-Out Tool Windows — Design

**Status:** Draft
**Date:** 2026-08-19
**Scope:** Any registered tool window — built-in (SFTP/file-explorer, Hosts/ssh-sessions, Tunnels) or plugin — can switch to "Window" view mode: its panel re-hosts in its own OS window with a dock-back affordance, IntelliJ-style. The capability is a platform trait carried by the tool-window registration contract, never per-panel opt-in.

## Product rules (settled in brainstorm, 2026-08-19)

1. **Platform trait:** if it registers with `toolWindowManager.register(id, …)`, it can pop out — plugin tool windows included, day one.
2. **View modes: Dock and Window only.** Float/always-on-top, pinned/unpinned auto-hide, drag-tear-off are out of scope (future features).
3. **The popped window's header carries a dock-back icon** (the IntelliJ affordance); dock-back returns the panel to the zone it came from.
4. **OS close = hide** (IntelliJ behavior): the tool window stays in Window mode; summoning it (rail icon, shortcut) re-shows the window. Dock-back is the only path back to the dock.
5. **Window mode and bounds persist** across restarts in the existing layout state; a Window-mode tool window that was visible reopens as a window at its saved bounds.

## Architecture

A pop-out is a fresh webview re-hosting the registered panel (webview DOM cannot move between windows — settings/chooser precedent). Rust owns window lifecycle via a registry; the popped webview boots `index.html` in a panel-host branch so every panel's dependencies exist by construction.

### Rust: `panel_host.rs`

- **Registry** (managed `Mutex`): keyed `(parent_label, tool_window_id)`; entries carry `req_id` (process-monotonic) and a request-unique `window_label` = `panelhost-<parent_label>-<req_id>` (unique labels are settled law: Tauri clears its label map only after the async destroy round-trips — same-label rebuild collides). All lookups by exact stored label; parent-derivation by label parsing is banned.
- **Commands:** `open_panel_host(window, tool_window_id, title) -> Result<u64, String>` (callers: main app windows only — reject `chooser-`/`settings`/`panelhost-` labels via `validate_panel_host_caller`; open against a live same-key entry = cancel-and-recreate, never adopt; returns the entry's `req_id`, the generation the frontend's stale-echo guard below compares against); `get_panel_host_request()` (exact window-label match → `{ reqId, toolWindowId, parentLabel, title }` camelCase); `panel_host_ready()` (show + focus; built `.visible(false)` with `arm_window_show_fallback`); `focus_panel_host(tool_window_id)`; `hide_panel_host(tool_window_id)`; `dock_panel_host(tool_window_id)`; `abort_panel_host()`.
  - `dock_panel_host` is callable from EITHER side, resolved by `resolve_dock_target`: the HOST window naming itself (its own dock-back button/menu), or the host's PARENT naming one of its own popped-out ids (the parent-side `View Mode: Dock` ruling — a parent needs a real teardown here, not a hide, because once the panel remounts into the zone a merely-hidden host would still be running a second live instance of the same stateful panel). Either way it emits `panel-host-docked {toolWindowId, reqId}` to the parent, removes the registry entry, then DESTROYS (never closes) the host window. Also the path `unregister()` takes on the frontend for a popped-out id going away (plugin removal): an orphaned host is destroyed, not hidden, for the same two-live-instances reason.
  - `abort_panel_host()` is the HOST's own self-close for "nothing to host here" — the boot's unknown/missing-tool-window-id path, and the no-pending-request path. Host-caller-only (`validate_panel_host_self_caller`); removes the entry, emits `panel-host-aborted {toolWindowId}` to the parent (resets that id's view mode to dock without expecting a remount — nothing was ever mounted), then destroys the window. A plain `window.close()` is the wrong tool here: for a still-REGISTERED host it would hit the `CloseRequested` hook below and be intercepted into a hide — a permanently invisible window with nothing in it.
- **Lifecycle hooks:** the host window's `CloseRequested` is intercepted — prevent close, `hide()` the window, emit `panel-host-hidden {toolWindowId}` to the parent (rail state sync). The webview and panel state survive; summon = `show()+set_focus()`. Parent `Destroyed` destroys all its panel hosts (exactly-once through the registry; late resolvers no-op). Dock-back, `abort_panel_host`, and displacement all destroy (not close — destroy skips CloseRequested; settled law).
- **Sizing:** default 520×400 logical floor, persisted per-tool-window bounds override (clamped to floor and monitor work area), centered on parent on first open, never moved/resized after show by us; user resizes/moves freely and bounds save on move/resize. **Bounds persistence is Rust-owned, not routed through the frontend's layout save** (the third scouting amendment): the window's own `Moved`/`Resized` events drive `schedule_bounds_persist`, a 500ms-debounced, per-window-label generation counter (`BOUNDS_SAVE_GENERATION`) that only the LAST event in a burst actually writes; the write itself (`persist_tool_window_bounds`) reads the live window's outer position / inner size directly and load-mutate-saves `PersistentState.layout.tool_window_bounds` — a `HashMap<String, WindowBoundsRecord>` keyed by `tool_window_id` **alone**, deliberately, not `(parent_label, tool_window_id)`: parent labels are launch-order-assigned and unstable across restarts, so a composite key would only accumulate orphaned records. The consequence, by design: the remembered bounds are ONE record shared across however many different parent windows have ever popped that id out — last writer wins. The live windows themselves stay fully independent; only the persisted, remembered size/position is shared.
- **Session resolution:** `effective_session_window_label` generalizes to consult BOTH the chooser registry and the panel-host registry (one resolver, one truth). Every session-keyed command (`sftp_*`, ssh channel queries a panel makes, plugin host-API calls that are window-scoped) resolves a `panelhost-*` caller to its parent. `tauri_host_api`'s window-scoped fields (appearance/dark-mode noted in the terminal-themes review) resolve the parent likewise.

### The trait surface (frontend, `toolWindowManager`)

- Per-id view-mode state: `'dock' | 'window'`, default `'dock'`, stored beside the existing zone assignments.
- Every tool window's context menu (built by the MANAGER, not panels — this is what makes the trait inheritable) gains View Mode entries. **Flattened, not a submenu** (the second scouting amendment): `tl-menu` has no submenu support, so this is two separate, sibling menu items — `View Mode: Dock` and `View Mode: Window` — with a checkmark on whichever is current, rather than a `Dock ✓ / Window` fly-out. `buildContextMenuItems(id)` carries both for every registered id, built-in or plugin, with no per-type special-casing.
- Choosing Window: panel unmounts from its zone (zone remembers the assignment for dock-back), `open_panel_host(id, title)` fires, rail icon stays lit while the window is visible. The request is claimed synchronously at REQUEST time, before the `invoke` even goes out (`markHostRequested` mints a per-attempt issue number) — this closes the window between asking and being answered so it is never mistaken for "no host is being built" by a fast second toggle.
- Rail-icon toggle routes by mode: dock → today's behavior; window → `focus_panel_host` when hidden/unfocused (falling back to a fresh `open_panel_host` if that answers `Err` — no host survived a relaunch), hide (`hide_panel_host`) when visible+focused (trace today's exact toggle semantics and mirror them).
- Dock-back is reachable from either side and both resolve to the same `dock_panel_host(tool_window_id)` call, dual-callable as described above: from the popped window's own header Dock button/menu (host-caller), or from the tool window's rail icon on the PARENT itself via `View Mode: Dock` while it is still popped out (parent-caller). Either way: Rust emits `panel-host-docked {toolWindowId, reqId}` → the parent remounts the panel into its remembered zone with a FRESH renderFn call (render-once; never a DOM move) → Rust destroys the host window. Unregistering a popped-out id (a plugin going away) takes the same `dock_panel_host` path to destroy its orphaned host, rather than leaving a hidden webview with no rail entry and no summon path back to it.
- **The stale-echo guard.** `open_panel_host` is async, so the frontend can legitimately fire a second pop-out attempt for the same id before an earlier one's promise has resolved (Window → Dock → Window again, fast). The `req_id` `open_panel_host` returns becomes that id's current generation (`hostReqIds`); `panel-host-docked`'s `reqId` field is compared against it, and an echo naming an older generation is dropped rather than remounting a panel that is actually live inside the newer host window. The comparison is keyed on the per-attempt issue number claimed above, not merely "is this id still in window mode" — a check against mode alone would resurrect an ABANDONED attempt's generation the moment a later pop-out put the id back into window mode, letting a stale echo match it. An echo with no stored generation at all (the post-relaunch `focus_panel_host`-only path, which never called `open_panel_host` and so never claimed one) is accepted, not dropped — there is nothing to disagree with.

### The panel host boot (`index.html`, boot branch)

- No new HTML entry, and **no query-string flag either** (the first scouting amendment): `open_panel_host` builds the window with a plain `index.html` URL. The branch is identified by the window's own Tauri LABEL, not a URL parameter — `main-runtime.js` fetches `current_window_label` and checks it for a `panelhost-` prefix EARLY, before any terminal/compose/manager initialization runs, and hands off to `panel-host-runtime.js`'s `boot()`. That boot then asks Rust what it was actually opened for via `get_panel_host_request()` (exact window-label match), rather than trusting anything carried in the URL.
- A panel-host boot skips terminal/PTY/tab-bar/titlebar-menu initialization entirely and instead: initializes config + appearance (`appearance.js` — the host follows app appearance like every window, via the same sequence settings.html's boot block uses: appearance resolves first, then the theme fetch that carries the resolved value), the plugin-widget bridge (with no terminal callbacks — `createTab`/`renameActiveTab`/`renameTabById`/`focusTabById`/`writeToActivePty` are all absent, so a plugin's tab/pty actions are inert here rather than half-working against panes that do not exist), and the tool-window REGISTRATIONS ONLY (`registrationsOnly: true` — no zones, strips, rails, or layout of any kind); calls `get_panel_host_request()`; renders the host chrome (slim header: tool-window title, dock-back button, plus the Windows/Linux window-controls cluster below); asks `toolWindowManager`'s registration table for the panel with the requested id and mounts it full-height; calls `panel_host_ready()`. Unknown/missing id, or no pending request at all, → `abort_panel_host()` self-close (a host with no panel must not linger; chooser precedent).
- **A host installs ZERO keyboard-router handlers — not "scoped" handling, none at all.** The draft's original "keyboard shortcut handling scoped to the host" undersold what actually had to be true: a host has no shortcut-runtime, so if anything upstream ever registers a handler in one, there is nothing there to outrank it. That gap was real — the plugin-registration path used to call the app titlebar's `refresh()`, and an UNINITIALIZED `refresh()` still publishes ~18 dead app-menu accelerator bindings (Cmd/Ctrl+W among them) into the keyboard router at priority 115 with a null action handler; in a main window `shortcut-runtime` outranks them at priority 120, but a host has nothing at that priority, so they would win outright and turn those combos into dead keys. The fix is at the call site, not a guard on `refresh()` itself (which is also called, harmlessly masked by priority, from real main windows and the settings modal): the plugin registration pass in a host runs with `chrome: false`, which never calls `titlebar.refresh()` in a host at all. The result: Cmd+W (etc.) in a host does nothing, full stop — not swallowed, not misrouted, just genuinely unbound.
- The host window participates in `config-changed` and `tl-appearance-changed` exactly as settings/chooser do (`appearance-sync.js`, wired in `panel-host-runtime.js` the same way settings.html wires it).
- **Windows/Linux window-controls cluster.** A panel host is built without native decorations on Windows/Linux (`create_panel_host_window`'s `use_custom_titlebar = cfg!(target_os = "windows") || cfg!(target_os = "linux")`), mirroring the chooser/settings windows. `panel-host-runtime.js`'s chrome builder gates on the SAME app-config `platform` field settings.html reads, and on that gate ONLY builds a minimize/maximize/close cluster into the header (nothing extra in the DOM on macOS, which keeps native traffic lights). Minimize and maximize/restore call the current window directly; close calls `currentWindow.close()` — the SAME `CloseRequested` path a native close control would raise, which the `CloseRequested` hook above converts into a hide. There is no separate "real" close wired through this cluster; OS-close = hide holds regardless of which chrome supplied the click.

### The parent-state event bridge (closed list)

Panels consume (a) app-global Rust broadcasts — `config-changed`, transfer progress, plugin events — which reach the host for free; and (b) parent-window state, bridged explicitly:

- `active-pane-changed` — payload: the parent's focused pane identity (pane id, kind, session key if remote). Consumer: files-panel's `onTabChanged` (SFTP follows the parent's active tab).
- Anything else the per-panel dependency audit (plan Task 1) surfaces becomes a NAMED addition to this list in the spec via spec-sync; the bridge API refuses unlisted event names (a constant array, not a passthrough — an unbounded bridge is how this rots).

Mechanism: parent runtime calls `panel_host_broadcast(event, payload)` → Rust `emit_to`s every live host of that parent → host runtime re-dispatches to the mounted panel through the same callback interface the manager uses in-window.

### Persistence

Two DIFFERENT paths, not one, despite both landing in `PersistentState.layout` (the third scouting amendment splits what the draft had lumped together):

- **View mode** persists through the EXISTING frontend layout save, the same way `tool_window_zones` / `active_tool_windows` already do: `tool_window_view_modes` (a `HashMap<String, String>`) rides along in the `save_window_layout` payload the frontend already sends on every layout change, merged into persisted state only when present (`commands.rs`), and read back into `SavedLayout` alongside the existing keys. Absent keys default to dock — old state files load unchanged. On launch, a Window-mode tool window that was visible at save time is summoned (`focus_panel_host`, falling back to `open_panel_host` since no host survives a relaunch); hidden ones wait for summon. Plugin tool-window ids persist the same way (ids are stable strings).
- **Window bounds** persist through a SEPARATE, Rust-owned mechanism with no frontend involvement at all: see the Sizing bullet above (`tool_window_bounds: HashMap<String, WindowBoundsRecord>`, keyed by `tool_window_id` alone, written directly off the host window's own `Moved`/`Resized` events, debounced). On launch, a Window-mode tool window that was visible at save time reopens as a window at its CLAMPED bounds (floor + monitor work area); a tool window with no saved bounds record falls back to the 520×400 default, centered on the parent.

## Non-Goals

- Float/always-on-top mode; pinned/unpinned auto-hide; Undock; Move-to-zone changes (exists or not, untouched).
- Drag-to-tear-off; menu-only in v1.
- Moving a panel between different MAIN windows; a pop-out belongs to the parent that opened it.
- Multi-panel tabs inside one popped window.
- Popping out the editor, terminal panes, or the settings/chooser surfaces (not tool windows).

## Known limitations

- A popped panel's webview survives hide (state preserved) but not app restart (panel state resets; window mode/bounds persist).
- A host installs NO keyboard-router handlers at all — not shortcuts "scoped to the host," genuinely none. Every combo that would otherwise act on "the current terminal pane," including Cmd/Ctrl+W, is simply unbound inside a panel host; see the panel host boot section above for the dead-keys bug this used to be (dead app-menu accelerator bindings winning by default in a window with no shortcut-runtime to outrank them) and the `chrome: false` fix.
- Popped-out bounds are keyed by `tool_window_id` alone, not per-parent: if the same tool window is popped out from two different main windows, the remembered size/position is ONE shared record and the last one to move/resize it wins. The live windows stay independent; only what gets remembered for next time is shared. Deliberate (parent labels are not stable across restarts), not a bug.
- The Windows/Linux window-controls cluster is exactly that — Windows/Linux only. macOS panel hosts keep native decorations (traffic lights) and never build the custom cluster at all.
