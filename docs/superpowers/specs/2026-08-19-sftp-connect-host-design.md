# SFTP Panel Independent Host Connections — Design

**Status:** Draft
**Date:** 2026-08-19
**Scope:** The SFTP tool window's remote pane gains a host dropdown that connects to any configured host on demand — no terminal tab required — with vault-unlock and password prompts where credentials need them. Connections are first-class sessions the whole app sees.

## Product rules (settled in brainstorm, 2026-08-19)

1. **First-class sessions:** a dropdown-initiated connection registers a real session (like a terminal SSH tab, minus the PTY). It appears in the chooser's Hosts sidebar, the Hosts panel's session awareness, and the editor can save through it. One connection model.
2. **Auth ladder:** vault credentials first (silent when unlocked and stored); locked vault → master-password unlock prompt then retry; no stored password (and key auth failed/absent) → one-shot password dialog with a "Save to vault" checkbox. Prompts chain (unlock → then password prompt if the account still has none). Cancel at any prompt aborts the connect cleanly.
3. **Key auth** (identity files) works silently when configured — no prompt.
4. **No auto-connect, no auto-reconnect:** connecting is always an explicit pick; a dropped session shows the existing error/failed state and reconnect is re-picking the host.

## Context (verified 2026-08-19 at main a062eca)

- Sessions: `RemoteState.sessions` keyed `"{window_label}:{pane_id}"`; shared `SshConnection`s keyed `"conn:{window_label}:{pane_id}"`, referenced by `connection_id` (`SshSession`, `remote/mod.rs:487-503`).
- Hosts: `remote_get_servers` returns the configured tree (folders + servers; ssh-config import exists via `remote_import_ssh_config`). `find_server_by_entry_id` (`server_commands.rs:340`).
- Vault: `try_vault_credentials(&vault, &server)` (`ssh_commands.rs:508`, used by the connect path at `:86`), `is_locked` checks, `vault_unlock` (`vault_commands.rs:137`).
- Session consumers: the chooser sidebar and files panel consume `remote_get_sessions` → `ActiveSession {key, host, user, port}`; scope objects carry `paneId` parsed from context; SFTP commands take `pane_id` + resolve the window via the shared caller→parent resolver.

## Design

### Rust: detached sessions (`remote/detached_commands.rs`)

- **Pseudo-pane ids:** `pub(crate) const DETACHED_PANE_ID_BASE: u32 = 1_000_000` (`detached_commands.rs:54`) — a **numeric** reserved range, not string ids. One process-wide `AtomicU32` (`NEXT_DETACHED_PANE_ID`), not a per-window allocator: session keys are already `"{window_label}:{pane_id}"`, so uniqueness is only required *within* a window, and a globally monotone counter is a strict superset of that. `mint_pane_id` re-seeds to the base if the counter ever wraps past `u32::MAX` (~4.29 billion detached connects in one process), so the invariant is structural rather than merely probable. Session key stays the existing `"{window_label}:{pane_id}"` format — just with a large numeric `pane_id` instead of a small sequential one — and flows through the EXISTING `SshSession`/`SshConnection` types unchanged. Every pane-id consumer audited by Task 1 was fixed to treat ids opaquely (compare, don't parse-as-small-int), never the reverse.
- **Command:** `sftp_connect_host(window, app, remote, vault, server_entry_id: String) -> Result<ConnectedSession, SftpConnectError>` where `ConnectedSession {sessionKey, host, user, port, paneId}` (camelCase; `paneId: number`) and `SftpConnectError` is internally tagged on `kind`: `VaultLocked`, `NeedsPassword {hasVaultAccount: bool}`, `AuthFailed {message}`, `Unreachable {message}`, `Other {message}`, and `ConnectInProgress` (execution addition, below). The command resolves the entry, then: an already-open detached session for this (window, entry) is handed back verbatim (duplicate-connect reuse, below); otherwise stored vault credentials (when unlocked) → key auth per server config → a typed error for the frontend to drive prompts. The caller's window label resolves through the shared caller→parent resolver (`session_caller_label`) — a popped-out panel connects on behalf of its parent, keyed under the PARENT's label.
- **Duplicate-connect reuse:** before touching the vault or the network, `find_detached_session_for_entry(state, window_label, entry_id)` checks for an existing detached session on this exact (resolved window, server entry) pair and returns its `ConnectedSession` unchanged if found — picking the same host twice cannot open a second connection. Scoped deliberately: a different window is an independent connection by product rule, and a terminal session on the same host is excluded twice over (its pane id is below the base, and it carries no `server_entry_id`). Not applied to `sftp_connect_host_with_password` — that command is only reachable after a `NeedsPassword`, which by construction means no session exists yet, and returning a stale one there would silently skip the `save_to_vault` the user just asked for.
- **In-flight guard:** `IN_FLIGHT_CONNECTS`, a process-wide set keyed `(resolved window label, server entry id)`, closes the window between a connect starting and its session being registered (a full network round-trip, plus a password dialog on the with-password path) during which the duplicate-connect check above sees nothing yet. `begin_connect` claims the key or returns `None` (→ `ConnectInProgress`); the returned `InFlightGuard` is RAII — it releases the key on every exit from the command: success, a typed error, or an early `?` (including a panic, via `Drop`). Both connect commands share the key, so a password submit cannot race a plain connect for the same host either. In `sftp_connect_host` the claim is taken AFTER the duplicate-connect check, so a pick that follows a just-completed connect still returns the open session rather than a busy signal.
- **`ConnectInProgress`:** a no-fields variant meaning a connect for this exact (window, entry) is already running. It is **not a failure** — the frontend treats it as retry-after-current: the in-flight connect will either produce the session (which the next pick hands straight back through the duplicate-connect guard) or fail with a variant of its own, and the caller's busy UI state is left exactly as it was rather than being cleared or routed to the error strip.
- **Command:** `sftp_connect_host_with_password(window, app, remote, vault, server_entry_id, password: String, save_to_vault: bool) -> Result<ConnectedSession, SftpConnectError>` — one-shot password attempt. On success with `save_to_vault`, `link_password_account` re-reads the entry's CURRENT `vault_account_id` from live `RemoteState` inside the lock that also performs the write (not the connect-time snapshot — closing a race where two concurrent saves for the same unlinked host could otherwise each take the "create" branch and orphan one account): an already-linked account is updated via `vault_update_account` (see preserve-key semantics below); an unlinked one is created via `vault_add_account` and then auto-linked — `entry.vault_account_id = Some(uuid)` followed by `save_server_preserving_folder` (an extraction of `remote_save_server`'s body, called `upsert_server`, that looks the entry's folder up first so a background link never silently moves a foldered host to the ungrouped list). A failed vault write does not fail the connect — the connection is what the user asked for; the write is logged as a warning naming the server label only. Password never logged, held only for the duration of the attempt.
- **`vault_update_account` preserve-key semantics:** updating an already-linked account (the `hasVaultAccount: true` rung, or a repeat save) is built by a pure `password_update_request`, which **preserves a key the account already carries** — `vault_update_account` replaces the whole `AuthMethod`, so a `Key` or `KeyAndPassword` account is rewritten as `key_and_password` carrying the original `key_path` and passphrase forward rather than being overwritten to a bare `password` method that would silently delete the key.
- **Command:** `sftp_disconnect(window, app, remote, session_key: String) -> Result<(), String>` — tears down a DETACHED session (pane id ≥ `DETACHED_PANE_ID_BASE` only); refuses (identical `"Not a detached SFTP session"` `Err` for every rejection reason — terminal-owned id, another window's session, unparseable tail — so the error can't be used to probe whether a session exists) for anything else. Idempotent: a repeat call on an already-gone key finds nothing, returns `Ok(())`, and skips the event.
- **Events:** `remote-sessions-changed` (`SESSIONS_CHANGED_EVENT`, `detached_commands.rs:60`) — no session-change event existed before this plan; this one is introduced by it and stays scoped to session-set changes. Emitted from exactly two call sites: `emit_sessions_changed` inside `detached_commands.rs` itself (on a successful connect and on a disconnect that actually removed something), and once more from `lib.rs`'s window-destroy handler, immediately after `cleanup::cleanup_ssh_sessions` reports it removed at least one session for the closing window (a detached session is one first-class casualty among possibly several; `cleanup.rs` itself stays a pure state function and never emits anything, so the event's only emitters are `detached_commands.rs` and the `lib.rs` handler that already holds the live `AppHandle`).

### Frontend: the dropdown (files-panel remote pane toolbar)

- A `tl-combo` in the remote pane toolbar: **"Follow active tab"** (default — today's implicit behavior made visible) → connected sessions (label `user@host` + `(pane N)` disambiguation via the existing `sessionHostLabel`) → separator → configured hosts from `remote_get_servers` flattened with folder prefixes ("Work / build-box"), built by `buildConfiguredHostOptions` (`files-panel.js`). Picking a session binds the pane (pins it); picking a configured host runs the connect flow then binds; "Follow active tab" unpins.
- **ssh-config dedupe:** `buildConfiguredHostOptions` walks folders, then ungrouped, then `ssh_config`, tracking seen entry ids and skipping any id already claimed — so a folder/ungrouped (config-owned) copy always wins over its `ssh_config` twin. This matters because saving to the vault from an ssh-config host **promotes** it: `~/.ssh/config` entries live only in `state.ssh_config_entries` (re-parsed every launch, so they can't carry a vault link), so `save_server_preserving_folder` writes a config-owned copy — the same promotion the Hosts UI already performs when an imported host is saved — and `find_server_by_entry_id` checks `config` before `ssh_config_entries`, so subsequent connects use the linked copy. Without the combo's dedupe, a promoted host would list twice (its original ssh-config entry and its new config-owned copy share one id but would otherwise appear as two options).
- Connect-in-progress: combo shows a busy state (`hostConnectBusyEntryId`); failures land in the panel's existing `.fp-error` strip. A `connectInProgress` response leaves the busy state untouched rather than clearing it. Busy clears on this window's own connect resolving (success or the auth chain giving up, both handled directly in `connectToHost`) or, for the `connectInProgress` case specifically, once a `remote-sessions-changed` refresh shows the busy entry's session has actually appeared (`refreshHostCombo`, scoped by host+port match — an unrelated sessions-changed event must not clear it). No client-side retry loop; a failed winner emits no event at all, so a busy connect left waiting on a failed racer stays busy until the user's own next pick. A detached session bound to the pane shows a disconnect button (⏏) beside the combo, gated on the pinned session's pane-id tail being `>= 1_000_000` (a frontend-side duplicate of `DETACHED_PANE_ID_BASE`, documented in-line as such since the Rust constant can't be imported); disconnecting returns the pane to "Follow active tab".
- Pinning is per-pane UI state (not persisted in v1); it is checked ahead of the existing `onTabChanged` tab-follow gate (that gate's own line is untouched), so a pin survives tab switches until explicitly cleared, and clearing it (`pinRemotePane(null)`) restores follow behavior on the pane's next tab-change event.

### Frontend: the auth dialogs (`features/files/connect-auth.js`, shared helpers)

Small tl-dialogs raised in the panel's own window (works docked and in panel hosts — tl-dialog is loaded in both), built via `document.createElement` (never innerHTML/querySelector, following `file-dialog-view.js`'s `confirmOverwrite` idiom):
- **Vault unlock:** master password field, error line on wrong password (a fresh dialog reopened per attempt, not patched in place), Cancel aborts. On success, retry `sftp_connect_host` once; if it now returns `NeedsPassword`, chain into:
- **Host password:** title `user@host`, password field, `Save to vault` checkbox (checked default when the host has a vault account, unchecked otherwise), Connect/Cancel. Wrong password → error line, re-prompt (attempt counter shown once 2 attempts have already failed, i.e. on the dialog for the 3rd try, reading "Attempt 3"). Cancel aborts.
- Both dialogs clear their password fields on close (`onClose`, which fires for every close path — Cancel, submit, Escape, backdrop); values live only in the invoke payload.

**Chain entry point — `connectAuth.run(serverEntryId, startingError, {invoke, data, onError})`.** Deviates from an earlier `run(serverEntryId, deps)` sketch by taking the triggering error as an explicit second argument. `files-panel.js`'s `connectToHost` still makes the FIRST `sftp_connect_host` call itself and still special-cases `connectInProgress` inline before ever calling `run()` — `connectAuth.run` has no access to `connectToHost`'s private `hostConnectBusyEntryId` closure variable, which is what "leave the busy state alone on `connectInProgress`" requires, so that one rung stays with the caller that owns the state. `run()` is handed only the *other* non-Ok error kinds, plus the error that triggered the handoff, and never repeats the first call redundantly. `vaultLocked` retries `sftp_connect_host` once itself (chaining into `needsPassword` if that retry needs one); `needsPassword` goes straight to the host-password loop; any other starting kind (`authFailed`/`unreachable`/`other`) routes to `onError` with no dialog. `run()` never rejects — it resolves with the won `ConnectedSession` or `null` (cancelled, or already routed to `onError`).

### Cross-surface consequences (by construction, verified in testing)

- Chooser sidebar lists detached sessions (it consumes `remote_get_sessions`); the editor saves through them (scope carries the pseudo paneId; SFTP commands accept it); popped-out panels connect on behalf of their parent via the resolver. No chooser-side connect UI in this project.

## Non-Goals

- No auto-connect/reconnect; no connection health polling.
- No chooser-side host dropdown (its sidebar inherits sessions; connecting from the chooser is a later feature).
- No per-pane persistence of the pinned host across restarts (v1).
- No changes to terminal SSH tab lifecycle or keying.
- No new credential storage outside the vault.
- No ssh-agent support: `termlab_remote`'s key auth reads identity files only, and this plan does not add agent support — key auth in the product rules above means identity files, not "agent or identity files."

## Testing

- **Rust:** pseudo-pane allocator (base respected, strictly monotone, a wrapped counter never mints into terminal id space, concurrent mints stay unique); `SftpConnectError` variant mapping (locked vault → `VaultLocked`, no other attempt; unlocked-but-passwordless account → `NeedsPassword{hasVaultAccount:true}`; no account → `NeedsPassword{hasVaultAccount:false}`; transport failure → `Unreachable`; a suppressed password prompt can never rewrite a transport failure); `sftp_disconnect` refuses numeric-below-base and out-of-window keys with an identical message, tears down detached sessions exactly-once, and is idempotent on a repeat call; `remote_get_sessions`/`active_sessions` includes a detached session alongside a terminal one; duplicate-connect reuse returns the same `sessionKey`/`paneId` and is scoped to (window, entry) — a terminal session is never handed out as a detached one; the in-flight guard blocks a second connect until the first releases (claim/reject/release-on-drop) and is scoped to (window, entry); `vault_update_account` preserves an existing key when a password is added (`Key`/`KeyAndPassword` → `key_and_password`, key and passphrase carried forward); the concurrent-link race (two `save_to_vault` calls racing on the same unlinked host) links exactly one account and orphans nothing, proven red-before-fix by swapping the live re-read for the connect-time snapshot; `connect_errors_serialize_tagged_and_camel_case` covers all six `kind` values including `connectInProgress`.
- **Frontend:** combo composition (follow + sessions + separator + flattened, folder-prefixed, deduped hosts — a config-owned copy beats its ssh-config twin sharing an id); re-attach after a forced re-render (`pane-view.js`'s `innerHTML`-based `renderPane` rebuilds the combo's `<select>` from scratch every call via `onComboMount`, so a stale-listener trap is structurally impossible); pick-host drives the connect invoke; `VaultLocked` → unlock dialog → retry chain; `NeedsPassword` → password dialog with checkbox default by `hasVaultAccount`; `connectInProgress` leaves the busy state untouched, never reaches the error strip; cancel-at-each-rung aborts with pane unchanged; wrong-password re-prompt with a growing attempt count; disconnect returns to follow mode; error strip on hard failures; password field cleared on close (assert the DOM); pin suppresses `onTabChanged` rebinding, unpin restores it on the next tab event.
- **Manual checklist section M** (`docs/superpowers/notes/light-editor-manual-checklist.md`, steps 147-161): fresh launch, locked vault, connect to a real host → unlock prompt → connected; wrong master password re-prompts; host without stored password → prompt (checkbox default by host) → save-to-vault → disconnect → reconnect silently; a key-auth host connects with no prompt; a key-only host with bad keys errors without ever showing a password dialog; cancel at each rung leaves the pane on its prior state; `[SSH]` editor saves through a dropdown session; chooser sidebar shows it; popped-out SFTP panel runs the whole flow (dialogs in the host window, transfers working through the resolver fix); two windows connect to the same host independently; a fast double-pick does not open a second connection; an ssh-config host promoted by a vault save appears once in the combo, not twice; pin survives tab switching; a dead-network host surfaces `Unreachable` in the error strip, not a password dialog; a judgment call on combo grouping/density, dialog copy, and attempt-counter tone.

## Known limitations

- A detached session dropped by the network shows as a failed scope on next use; no background liveness check ever proactively detects a dead detached session — it is only discovered on the next use (F2, deferred from Task 2's review; carried here rather than fixed, since the product rules explicitly rule out connection health polling).
- Pinning resets to "Follow active tab" on app restart.
- ssh-config promotion is deliberate, not a bug: saving a password to the vault for an ssh-config-discovered host writes a config-owned copy of that entry (the only way it can carry a `vault_account_id`, since `~/.ssh/config` is re-parsed every launch). The combo's dedupe keeps this invisible to the user, but a script or export that reads `remote_get_servers` directly will see both the original ssh-config entry and its promoted copy sharing one id.
